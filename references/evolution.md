# 自我进化机制（Estrella 车机 APK 打包 Skill）

本 Skill 的「自我进化」全部发生在**服务器端**（106.12.162.224:7799），本地 Skill 只负责调用与展示。
本文档**如实**说明它到底能做什么、不能做什么，避免被误解为「AI 自动思考」。

## 一、进化的本质

它不是大模型微调，而是一个**结构化经验累积 + 检索加权 + 自动教训抽取**的闭环：

- 真正生成修复方案的，始终是 WorkBuddy 里的 LLM（本 Skill 的 7 步工作流）。
- 服务器负责把每次任务的「输入参数 / 尝试的修复 / 最终成败」沉淀下来，并在下次相似任务时，用更聪明的**检索与排序**把这些经验用起来。
- 进化 = **用得越多，推荐越准；犯过的错，下次自动绕开**。

## 二、它具体能做的事（实打实）

1. **同款车不同车机 → 自动区分，禁止死板复用**
   - 每台车机入库时由服务器计算「变体签名」= 对 `arch/chip/dpi/root_status/android版本/存储限制/权限限制/蓝牙限制/USB限制/已知bug` 的哈希。
   - 同 `vehicle_key`（车型+年份+系统版本+安卓版本）但参数签名不同 → 自动拆分变体并告警。
   - `recommend` 在变体不匹配时返回 `variant_mismatch=true`，Skill 被强制提示用户「先验证再套用」，从机制上杜绝「上次能修就直接抄」。

2. **方案按成败加权排序（confidence）**
   - 每个方案记录 `success_count / fail_count`，`confidence = 胜率 × 样本可信度`（样本越少越保守，上限 1.0）。
   - `recommend` 返回的方案已按 confidence 降序排列；`confidence<0.6` 的方案标为「需验证」而非「推荐直接套用」。

3. **失败自动生成「负向教训」坑（自动吸取教训）**
   - 用户回报 `outcome=fail` 时，服务器自动在该车型下新增一条 `tags:["negative_lesson"]` 的坑，
     根因写明「该修复在此车机变体失败，下次须重新评估，勿直接套用」。
   - 后续 `recommend` 会把这类坑作为高危警示返回，并拉低对应方案置信度 → **同一条错误不会第二次机械复用**。

4. **相似车型检索（无精确记录时的兜底参考）**
   - 无精确匹配时，按 `安卓版本(0.35)+架构(0.15)+芯片(0.15)+存储/权限/bug 重叠(0.4)` 加权相似度，
     返回 Top-3 相似车型及其最佳方案，明确标注「相似参考，非同款，须重新评估」。

5. **可追溯 + 可回滚**
   - 所有写操作（upsert / report_outcome / resolve）追加到不可变 `audit.log.jsonl`。
   - kb.json 每日自动备份（保留 30 天）。任何误写都能追责、能回滚。

6. **车型名归一（防分裂建库）**
   - `vehicle_key` 的车型段自动小写并去除全部空白；「逸动PLUS / 逸动 plus / 逸动Plus」归一为同一主键。
   - 历史非规范主键在服务加载时一次性重映射（并同步冲突引用），同款车不会因写法不同被拆成多条记录。

7. **安卓大版本漂移监控**
   - 车机跨安卓大版本（如历史基线 9.0 → 本次 11）时，`recommend` 返回 `android_drift=true` 并给出告警文案，`upsert` 也会记录漂移回执。
   - **绝不覆盖历史基线版本**，漂移版本另存于 `android_versions_seen`，并提示「旧方案须人工复核后再套用」。

8. **冲突半自动仲裁**
   - 冲突队列每条自动附 `suggest`：历史方案「有失败且零成功」→ 倾向 `apply_incoming`；「成功样本足且置信高」→ `keep_existing`；证据均不足 → `needs_review`。
   - `resolve --action auto` 可一键按建议裁决；若 `needs_review` 则服务端拒绝自动裁决并提示人工——**绝不强裁**。
   - 另有按 IP+Token 双维度限频，以及认证失败突发告警（写入审计日志）。

## 三、它做不到什么（诚实边界，别指望）

- ❌ **不能凭空发明新修复**：新方案仍由 LLM 基于当时问题生成；服务器只负责记与排。
- ❌ **不能验证修复是否真的有效**：除非用户回报 `report_outcome`，否则服务器不知道某次修复是否成功。
  → 所以「进化闭环」的第 8 步（请用户回报 + 调用 report_outcome）是**必须执行**的，缺了这步进化就断了。
- ❌ **不是语义级深度推理**：变体区分/相似度都是基于结构化字段的启发式哈希与加权，不是 embedding 语义理解。
  极端隐蔽的兼容性差异（字段上看不出来）仍可能漏判，此时依赖 `variant_mismatch` 的人工验证提醒兜底。
- ❌ **不会跨车型强行泛化**：相似车型只是参考，绝不会冒充同款自动套用。

## 四、数据流向（一次完整进化闭环）

```
用户提交车型+故障
   → Skill 调 recommend（查历史，判变体/置信度）
   → LLM 生成/选用修复 → 改码 → 构建 → 出包
   → 用户装包测试 → 回报 成功/失败
   → Skill 调 report_outcome（成功+1 / 失败+1 且自动生成负向教训坑）
   → 下次同/相似车型：recommend 已更聪明（避开失败、优先成功、区分变体）
```

## 五、运维

- 进化状态看板：`local_kb.py stats` → 关注「进化·负向教训数 / 同款车变体拆分 / 累计成败反馈 / 冲突可自动裁决」。
- 查看冲突与仲裁建议：`local_kb.py conflicts`；一键裁决：`local_kb.py resolve --conflict-id 「id」 --action auto`。
- 服务器进程：`systemctl status estrella-kb`；数据：`/opt/estrella-kb/data/kb.json` + `audit.log.jsonl` + `backups/`。
- 想清掉错误教训：进入 `/kb/conflicts` 复核或手动编辑 kb.json（需服务器权限）。
- Token 轮换：改 `/opt/estrella-kb/.env` 的 `KB_TOKEN`（systemd 以 `EnvironmentFile` 加载），`systemctl restart estrella-kb` 后同步 `scripts/local_kb.py` 默认值与 `references/locked-config.md`。
